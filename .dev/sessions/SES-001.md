### 1. [implementation] affichage de la version

Le présent répo fournit un système d'information outillé d'un cli. (pour l'instant) La version du cli est la même que la version du SI.

Dans cette première tâche, nous allons créer une première fonctionalité: l'affichage de la version courante de clia à partir de la commande `clia version`

La source de vérité de la version est le commit hash du repo. La version exacte est le hash d'un commit.

Des alias permettent de fournir une version sémantique (v<Major>.<Minor>.<Patch>[-<tag>]) lisible et signififiant pour un humain.


Cette alias de version lisible est inscrite dans l'entrée `version` dans le fichier `@clia.yaml` ou `.clia.yaml` ou `.dev/yaml`.

L'entrée `version` n'est pas une donnée 100% fiable. Elle dépend du mécanisme de publication et pourrait être fausse puisque le fichier `clia.yaml` peut ne pas être incrémenté à chaque commit.

C'est pourquoi, il faut toujours de fier au hash commit lorsqu'on a un besoin de validation.

Aussi, pour s'assurer de l'exactitude de la version, on doit vérifier le numéro de version des commits précédents.

Si le commit précédent a une `version` différente dans le fichier `clia.yaml`, la version courante est une version publiée.

Si le commit précédent a pas la même entrée `version` dans le fichier `clia.yaml`, la version courante est une version de travail. L'alias de cette version de travail et <version semantique>+<short hash commit>


Lexique:

- source de vérité de la version
- version exacte
- alias de version
- version publiée
- version de travail

Commande à implémenter => 

```sh
clia version # alias de version lisible
clia version --true # hash commit
```

### 2. [implémentation] Incrément de version

Modifier la version dans le fichier `clia.yaml` ou `.clia.yaml` ou `.dev/clia.yaml` et commiter

```sh
clia version release MAJOR|MINOR|PATCH
```

Pré-condition: le repo doit être propre.

Post-condition: la commande `clia version` rapporte 1. une version publiée et 2. une version supérieur à la version précédente et 3. une différence d'incrément à ce qui a été demandé `MAJOR|MINOR|PATCH`.

### 3. [implémentation] documentation

Toute commande et sous-commande et sous-sous-commande et ... a une documentation accessible dynamiquement:

```sh
clia -h|--help  # affiche une aide brève pour clia
clia CMD -h|--help # affiche une aide brève pour clia CMD
# ...
```

Combinée avec l'option `--man`, on affiche le manuel d'instruction complet au format d'un manuel unix/gnu/linux.

La version de base ne doit pas contenir d'information textuelle. Seulement une liste des commandes, la ou les signatures valides pour chaque commande ou sous-commande et les options disponibles.

La version longue explique ce que fait chaque commande, quels sont les variables et les output, leur formats, donne des détails du comportement, etc. 

Utiliser le format et les conventions d'usage des "manuel unix". pour plus d'information sur ce format et ces conventions, consulter internet ou la commande `man man`

### 4. [implementation] activation de clia dans un repo

Le script `setup.sh` fournit toutes les fonctionalités nécessaires à la gestion d'une installation de clia.

Définition: une "installation" est 
  - 1. un programme, un cli ou n'importe quel système d'information fournisant des fonctionalités spécifiques ;
  - 2. l'ensemble des variables d'environnement décrivant son mode d'intégration dans un autre système (OS, aplication hôte, ou autre) ; et
  - 3. l'ensemble des options modulant son fonctionnement

Une installation a:
  - une durée de vie
  - une source (exécutable et fichiers de support)
  - une portée (su quoi c'est utilisable)


```sh
# Rend actif la commande "activate" dans l'emplacement ROOT_PATH (défaut: ROOT_PATH=$PWD)
. setup.sh [-C ROOT_PATH] activate
```

Une "activation" est une installation qui a 
- une durée de vie limité à une session (bash) active,
- une source liée au script d'installation utilisé, et
- une portée limitée à un seul repo de travail.

### 5. [implementation] Ce qu'est une ressource

Les ressources informationnelles sont le fondement du système d'information clia.

- ils contiennent l'information nécessaire à la génération de livrables reproductible ou "primitive".
- Les primitives peuvent être fournies par un humain ou générés par un agent IA ou par un automatisme ou provenir d'une source d'information externe.

Une ressource a son propre cycle de vie. Une ressource a donc une version qui lui est propre.

Chaque ressource a un nom et un préfix. 

Une ressource:
- dit comment produire un ou des livrables d'une nature précise
- contient des primitives (ressources de conception)
- peut fournir des skills ou des scripts permettant de
  - valider les input et les outputs
  - agit sur les livrables associés ou sur les d'autres ressources ou d'autres fichiers ou d'autre information



Une instance de ressource:
  - contient des primitives
  - permettant de produire un ou des livrables associés à cette ressource
  - à partir des outils (skills, scripts, etc.)

### 17. [implement] upgrade|downgrade clia


clia agit sur le repo dans lequel on se trouve. Donc, `clia version` donne la version du repo courant.


Afficher la liste des version de clia disponible:

```sh
clia setup version  # version du cli utilisé

clia setup version ls # liste de toutes les versions disponibles 
```

Mettre à jour le repo courant:

```sh
clia upgrade|downgrade [--with-instances|--migrate] [--all] [CLIA_VERSION]
```

Ce que upgrade fait:
- met à jour les fichiers harnais, les ressources, les skills et les features de clia

Ce que fait l'option `--all`:
- met également à jour toutes les ressources

L'option `--with-instances` ou `--migrate` demande de migrer les instances des ressources

Pour mettre à jour uniquement une ressource =>

```sh
clia RESSOURCE upgrade|downgrade [--with-instances|--migrate] [RESSOURCE_VERSION] 
```

Sans no de version, on utilise la dernière version disponible.

Upgrade signifie que la version cible doit être supérieur à la version courante.

Downgrade signifie que la version cible doit être inférieur à la version courante.

### 19. [refactor] ressource primitives, ressources livrées et ressource installée

#### Ressource

Définition conceptuelle: Une ressource est un ensemble d'informations manipulables et utiles pour réaliser une intention.

#### Ressource clia

Une ressource clia est un ressource compatible avec le système clia pour une version donnée.

Les instances de ressource clia se trouvent dans $CLIA_ZONE_RESSOURCE/RES-<SEQ>-<SLUG>/

Par défaut, CLIA_ZONE_RESSOURCE=@.dev/ressources

#### Primitives de ressources de premier et de 2e ordre

Ce répertoire contient les primitives de premier ordre (primitive-1), les primitives de 2e ordre (primitive-2) au besoin et les livrables.

Une primitive de premier ordre est un fichier input que seul un humain peut écrire.

Une primitive de 2e ordre est une primitive mixte qui peut être généré par un agent IA et/ou générer d'un automatisme et/ou provenir d'une source externe et/ou modifié par un humain. 


$CLIA_ZONE_RESSOURCE/{primitive-1,primitive-2}


Une ressource peut être primitive d'une autre ressource. Une ressource primitive est nécessairement une ressource d'ordre 2.


#### Ressource livrée ou instance d'une ressource

Un livrable est un objet utilisable en soi.

Une ressource livrées peuvent être produites manuellement ou générées par un automatisme ou générées par un agent IA.

Elles se retrouvent dans @


#### Ressource installé

Une ressource clia installé est utilisable (fonctionnalités, skill et scripts).

Les ressources se retrouvent dans $CLIA_ZONE_RESSOURCE_LIVREE/*

Où, par defaut, CLIA_ZONE_RESSOURCE_LIVREE=@.clia/ressources

Seuls les ressources livrées sont accessibles par le cli.

Seul les commandes cli (upgrade|downgrade|activate|deactivate|install|uninstall) sont autorisées à installer, désintaller, activer, désactiver ou modifier les ressources installées.

La version des ressources installés sont figées.

Les ressources installés peuvent être ajouter au code source ou pas (mettre CLIA_ZONE_RESSOURCE_LIVREE)

**restriction**: les agents IA ne doivent pas toucher aux ressources installés. 

**autorisation**: les agents IA on droit d'utiliser les commandes fournis par les ressources.

### 24. [feature] polymorphisme des ressources

Une ressources clia est reconnaissable par une chose: elle a des informations d'identification et d'essentialisation (IIE).

Ces IIE sont implémentés communément sous forme de données structurées contenant un identifiant et les propriétés essentielles.

Une ressource contient 3 types d'information:
- les information d'identité qui permettent d'attester de l'unicité de la ressource
- les informations essentielles qui définisent ce qu'est cette ressource
- les informations accidentelles qui décrivent comment elle est, ce qui lui est arrivé, etc.


L'information d'identité est polymorphe: elle peut prendre plusieurs formes selon le contexte.

Forme absolue: `clia:<uuid>`

Forme relative à un repo: `<PREFIX>-<SEQ>`

Forme partageable: `<NAMESPACE>/<PREFIX>-<SEQ>`

Où le NAMESPACE est une string d'"autorité" contrôlé par l'éditeur. exemple: clia.noumanity.com pour le repo clia édité par Groupe Innovation Numanity inc. 

---

Une ressource clia peut prendre la forme d'un fichier unique.

Dans ce cas, l'IIE est soit interne, soit externe.


Dans le cas interne, l'IIE est dans le fichier sous forme de données structurées: une partie des données structurées (dans le cas d'un fichier qui est une donnée structurée), "frontmatter" ou en commentaire (selon le type du fichier).

Dans le cas externe, l'IIE est dans un fichier structuré et elle DOIT inclure l'information vers une représentation de la ressource. Typiquement un URI

---

Ce qui vient d'être décrit précédement pour un fichier :
- une ressource == IIE + une représentation
- l'IEE est interne ou externe à la ressource

est également vrai pour n'importe quelle forme de représentation, notamment 
1. un répertoire contenant des fichiers et répertoires imbriqués
2. un repo git


Dans ces cas, l'information pointant vers la représentation n'est plus seulement un URI

---

Une ressource peut être composé d'autres ressources.

Dans ce cas, pointer vers l'IIE de la ressource est suffisant pour désigner l'ensemble des fichiers de la ressource

---

IMPLÉMENTATION

- La ressource RES contient un script permettant de valider l'IIE.
- La ressource RES contient l'information ici décrit dans une primitive de type SPC, REQ et/ou NFR
- La présence d'un IIE est le premier critère de conformité de `clia RESSOURCE check`
- la commande `clia res ls` recherche 1. dans un repo, toutes IIE et 2. à l'extérieur d'un repo, 3. touts les repos qui sont des ressources ou, autrement dit, les repos qui ont un IIE identifiant ce repo comme une ressource clia.
