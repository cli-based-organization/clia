### 1. [implementation] affichage de la version

Le présent répo fournit un système d'information outillé d'un cli. (pour l'instant) La version du cli est la même que la version du SI.

Dans cette première tâche, nous allons créer une première fonctionalité: l'affichage de la version courante de clia à partir de la commande `clia version`

La source de vérité de la version est le commit hash du repo. La version exacte est le hash d'un commit.

Des alias permettent de fournir une version sémantique (v<Major>.<Minor>.<Patch>[-<tag>]) lisible et signififiant pour un humain.


Cette alias de version lisible est inscrite dans l'entrée `version` dans le fichier `@clia.yaml` ou `.clia.yaml` ou `.dev/yaml`.

L'entrée `version` n'est pas une donnée 100% fiable. Elle dépend du mécanisme de publication et pourrait être fausse puisque le fichier `clia.yaml` peut ne pas être incrémenté à chaque commit.

C'est pourquoi, il faut toujours de fier au hash commit lorsqu'on a un besoin de validation.

Aussi, pour s'assurer de l'exactitude de la version, on doit vérifier le numéro de version des commits précédents.

Si le commit précédent a une `version` différente dans le fichier `clia.yaml`, la version courante est une version publiée.

Si le commit précédent a pas la même entrée `version` dans le fichier `clia.yaml`, la version courante est une version de travail. L'alias de cette version de travail et <version semantique>+<short hash commit>


Lexique:

- source de vérité de la version
- version exacte
- alias de version
- version publiée
- version de travail

Commande à implémenter => 

```sh
clia version # alias de version lisible
clia version --true # hash commit
```

### 2. [implémentation] Incrément de version

Modifier la version dans le fichier `clia.yaml` ou `.clia.yaml` ou `.dev/clia.yaml` et commiter

```sh
clia version release MAJOR|MINOR|PATCH
```

Pré-condition: le repo doit être propre.

Post-condition: la commande `clia version` rapporte 1. une version publiée et 2. une version supérieur à la version précédente et 3. une différence d'incrément à ce qui a été demandé `MAJOR|MINOR|PATCH`.

### 3. [implémentation] documentation

Toute commande et sous-commande et sous-sous-commande et ... a une documentation accessible dynamiquement:

```sh
clia -h|--help  # affiche une aide brève pour clia
clia CMD -h|--help # affiche une aide brève pour clia CMD
# ...
```

Combinée avec l'option `--man`, on affiche le manuel d'instruction complet au format d'un manuel unix/gnu/linux.

La version de base ne doit pas contenir d'information textuelle. Seulement une liste des commandes, la ou les signatures valides pour chaque commande ou sous-commande et les options disponibles.

La version longue explique ce que fait chaque commande, quels sont les variables et les output, leur formats, donne des détails du comportement, etc. 

Utiliser le format et les conventions d'usage des "manuel unix". pour plus d'information sur ce format et ces conventions, consulter internet ou la commande `man man`

### 4. [implementation] activation de clia dans un repo

Le script `setup.sh` fournit toutes les fonctionalités nécessaires à la gestion d'une installation de clia.

Définition: une "installation" est 
  - 1. un programme, un cli ou n'importe quel système d'information fournisant des fonctionalités spécifiques ;
  - 2. l'ensemble des variables d'environnement décrivant son mode d'intégration dans un autre système (OS, aplication hôte, ou autre) ; et
  - 3. l'ensemble des options modulant son fonctionnement

Une installation a:
  - une durée de vie
  - une source (exécutable et fichiers de support)
  - une portée (su quoi c'est utilisable)


```sh
# Rend actif la commande "activate" dans l'emplacement ROOT_PATH (défaut: ROOT_PATH=$PWD)
. setup.sh [-C ROOT_PATH] activate
```

Une "activation" est une installation qui a 
- une durée de vie limité à une session (bash) active,
- une source liée au script d'installation utilisé, et
- une portée limitée à un seul repo de travail.

### 5. [implementation] Ce qu'est une ressource

Les ressources informationnelles sont le fondement du système d'information clia.

- ils contiennent l'information nécessaire à la génération de livrables reproductible ou "primitive".
- Les primitives peuvent être fournies par un humain ou générés par un agent IA ou par un automatisme ou provenir d'une source d'information externe.

Une ressource a son propre cycle de vie. Une ressource a donc une version qui lui est propre.

Chaque ressource a un nom et un préfix. 

Une ressource:
- dit comment produire un ou des livrables d'une nature précise
- contient des primitives (ressources de conception)
- peut fournir des skills ou des scripts permettant de
  - valider les input et les outputs
  - agit sur les livrables associés ou sur les d'autres ressources ou d'autres fichiers ou d'autre information



Une instance de ressource:
  - contient des primitives
  - permettant de produire un ou des livrables associés à cette ressource
  - à partir des outils (skills, scripts, etc.)

### 6. [implémentation] ressources harnais => HRN

Les ressources harnais (HRN) de clia fournissent des instructions aux agents IA et aux automatismes pour guider leur fonctionnement.

**Qu'est-ce qu'un repo clia**

un repo clia est un repo qui est capable de gérer des ressources informationnelles et des livrables avec le SI clia.

Pour être conforme, il doit avoir minimalement:

- un fichier état: `clia.yaml` ou `.clia.yaml` ou `.dev/clia.yaml`
- un fichier harnais IA principal (@CLAUDE.md)
- un fichier harnais IA @CONSTITUTION.md spécifiant les rôles et permissions pour chaque intervenant: humains, automatismes et agents IA





**vérification des harnais clia**

```sh
clia check # vérifie la conformité d'un repo clia
clia check --harness # dit si des harnais clia sont installés ou non et rapporte les problèmes
```


**installation des harnais clia**

```sh
clia init .|REPO_PATH # initialise un repo et ajoute l'état et les harnais IA
```

Post-condition: 
- REPO_PATH est un répo git
- le fichier CLAUDE.md existe
- le fichier CONSTITUTION.md existe

### 15. [implementation] ce que fournit une ressource

Une ressource apporte au projet:
- des fonctionalité (IA)
- des scripts
- des skills


```sh
# affiche ce qu'apporte une ressource
clia RESSOURCE provide [ls]

# Affiche la liste de toutes les fonctionnalités de toutes les ressources installés
clia features ls

# Affiche la liste de tous les scripts de toutes les ressources installés
clia scripts ls

# Affiche la liste de tous les skills de toutes les ressources installés
clia skill ls

```


Les fonctionnalités sont des extraits ajoutés aux fichiers harnais.

Les skills sont des skills ajouter dans .claude (ou autre selon le système IA utilisé) + directives/conditions d'utilisation de ce skill dans CLAUDE.md

Les scripts sont les commandes (CMD) fournies au cli `clia RESSOURCE CMD ...`

on peut toujours activer et désactiver ce qui est fourni par une ressource:

```sh
clia feature activate|deactivate FEATURE_NAME [RESSOURCE_PREFIX]
clia script activate|deactivate FEATURE_NAME [RESSOURCE_PREFIX]
clia skill activate|deactivate FEATURE_NAME [RESSOURCE_PREFIX]


```

### 16. [implementation] notion de focus

Fonctionnalité de base à clia permettant de concentrer l'attention de l'IA sur une quantité restreinte d'information.

Dire à claude de ne prendre en compte par défaut que les documents dans le répertoire @focus/

```sh
# ajoute une instance dans le focus
clia focus on <PREFIX>-<SEQ>
# ajoute un répertoire ou un fichier
clia focus on $INFO_PATH   # un prefix @ fait référence à la racine du repo courant

# retire le focus d'une information
clia unfocus FOCUSED_INFO

# affiche tous les documents dans le focus
clia focus ls

# retire tous les documents du focus
clia focus clear|clean|reset
```

Les fichiers dans @focus/ sont des fichiers symboliques.

Par défaut, ils ne sont pas ajoutés dans l'index de git (.gitignore)
